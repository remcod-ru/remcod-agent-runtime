# ADR-0003: Явная композиция runtime

- Status: Accepted
- Date: 2026-08-30

## Контекст

Поведение model/tool loop зависит от agent definition, provider, store, budgets, retry, compaction, clock и генерации идентификаторов. Если хотя бы часть этих зависимостей выбирается через process-wide registry или переменные окружения, одинаковый вызов public API может иметь разные semantics в тесте, приложении и после загрузки плагина.

## Решение

Все изменяющие execution semantics зависимости передаются через `RuntimeConfig`. `createRuntime` получает явный agent registry, делает его неизменяемый snapshot и отклоняет повторяющиеся ID; session выбирает ровно одного agent по `agentId` или завершается fail-closed. Defaults экспортируются как неизменяемые значения. Глобального registry и неявного environment lookup в core нет.

## Почему

Отвергнут глобальный service locator: он сокращает setup-код, но создаёт скрытый порядок инициализации и гонки между runtimes; цена — недетерминированные тесты и невозможность безопасно держать разные конфигурации в одном процессе. Отвергнут автоматический выбор provider и limits из окружения: он удобен для одного deployment, но превращает deployment configuration в часть протокольных semantics. Отвергнута горячая подмена agent definitions внутри уже созданного runtime: цена простоты обновления — сессии, чьё поведение меняется без версии или события. Цена выбранного решения — более многословный bootstrap и необходимость явно пересоздать runtime для новой agent-конфигурации.

## Последствия

Несколько runtimes могут безопасно сосуществовать и получать детерминированные test doubles для clock, IDs, store и provider seams. Интеграторы отвечают за композицию и lifecycle зависимостей. Добавление новой обязательной semantic dependency меняет `RuntimeConfig` и требует публичного review, а не скрытой инициализации.
